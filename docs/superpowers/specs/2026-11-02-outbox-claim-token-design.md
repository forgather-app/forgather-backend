# 아웃박스 선점 토큰 설계

관련 이슈: https://github.com/forgather-app/forgather-backend/issues/250

## 목적과 범위

현재 선점 토큰을 가진 작업자만 아웃박스 상태와 실패 횟수를 변경하도록 한다.
기존 SOCIAL_REVOKE, 스케줄러, 완료, 취소, 실패, 재시도 경로에 공통 적용한다.
PDF 도메인과 커밋 직후 실행은 #251에서 구현한다.

## 검토한 접근

1. 기존 PROCESSING 조건만 유지: 변경은 작지만 재선점 이전 작업자의 상태 변경을 허용한다.
2. 매 선점마다 새 UUID 토큰을 저장하고 결과 UPDATE에서 확인: 현재 작업자의 상태 변경 권한을 명확하게 보장한다.

사용자는 두 번째 접근을 선택했다. 외부 호출을 포함한 장시간 DB 잠금은 사용하지 않는다.

## 저장과 선점

- outbox에 nullable claim_token VARCHAR(36)을 추가한다. 기존 행은 NULL로 유지한다.
- 선점 시 UUID를 생성하고 기존 조건부 UPDATE에 토큰 저장을 추가한다.
- 최초 선점과 만료 후 재선점 모두 새 토큰을 사용한다.
- 선점 서비스는 성공 시 해당 호출이 생성한 토큰, 실패 시 빈 결과를 반환한다.
- 작업자는 선점 결과를 지역 변수로 보존한다. DB를 재조회해 다른 작업자의 토큰을 가져오지 않는다.
- 기존 REQUIRES_NEW 선점 및 상태 저장 트랜잭션을 유지한다.

## 상태 변경

- 완료, 취소, 실패, 재시도 UPDATE는 id, status = PROCESSING, claim_token 일치를 모두 요구한다.
- 기존 payload 보존 및 제거 규칙과 최대 실패 횟수 정책은 유지한다.
- PROCESSING에서 벗어나는 모든 전이에서 토큰과 lease_expires_at을 NULL로 정리한다.
- 다른 토큰이나 NULL 토큰으로 호출하면 변경 행 수가 0이 된다. 상태와 실패 횟수는 바뀌지 않는다.
- 선점 경쟁에서 패배하거나 결과 기록 권한을 잃은 작업은 성공한 상태 전이로 집계하지 않는다.

구현 제안: 만료 시각은 재선점 가능 여부를 결정한다. 아직 재선점되지 않아 토큰이 일치하면 기존 작업자의 결과를 허용한다. 결과 UPDATE에 만료 시각 조건은 추가하지 않는다.

## 보장과 한계

이전 작업자는 재선점 이후 성공과 실패 모두 기록할 수 없다. 이로 인해 이전 작업자의 실제 외부 성공도 버려질 수 있다.
토큰은 외부 실행 취소, 정확히 한 번 실행, 외부 서비스와 DB 간 원자성을 보장하지 않는다.

## 배포 전환

구버전 UPDATE에는 토큰 조건이 없어 신버전과 동시에 실행하면 정책을 보장할 수 없다.
마이그레이션은 nullable 컬럼 추가로 수행하되, 구버전 아웃박스 작업자를 중지하고 진행 중 호출의 종료를 확인한 뒤 신버전 처리를 시작한다.
기존 PROCESSING 행은 선점 만료 후 새 토큰으로 회수한다. 기존 행의 상태나 실패 횟수를 일괄 초기화하지 않는다.

## 검증

- 최초 선점, 동시 선점, 만료 후 재선점 및 토큰 교체
- A 선점 후 B 재선점: A의 완료, 취소, 실패, 재시도는 모두 거절
- 위 거절 이후 B의 상태와 실패 횟수 및 payload와 토큰 보존
- 현재 토큰의 완료, 취소, 실패, 재시도 성공 및 토큰 정리
- NULL 또는 잘못된 토큰 거절
- 기존 최대 실패 횟수 및 SOCIAL_REVOKE 처리 회귀
- 실제 외부 API 없이 단위 테스트와 MySQL Testcontainers 테스트 실행
